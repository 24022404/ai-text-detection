The system’s implementation of social login is comprehensively designed to simplify and secure user authentication while also providing robust options for private key management, as illustrated in Figures 4.2, 4.3, and 4.4. In the sign-up scenario depicted in Figure 4.2, the user initiates account creation by selecting their preferred social identity provider, prompting a series of interactions between the user, the system, the integrated SDK, Executors, and the authentication platform Auth0. The SDK serves as the main interface, guiding the process of credential submission and communication with Auth0, which validates the user's credentials and issues a secure authentication token. This token enables the system to generate a new user key pair, ensuring that private keys are created securely and associated with the correct user identity. The generated key pair is then safely stored, with only encrypted shares or references retained within the system to enhance security and support future recovery scenarios. Throughout this process, Executors play a vital role in facilitating, verifying, or performing certain cryptographic operations as delegated by the system or SDK, thus maintaining a secure and modular architecture. Should errors occur at any stage—whether due to user input, network issues, or service unavailability—the system is equipped to handle them gracefully, as prompt error messages are relayed via the SDK, and potential error codes are catalogued in Table 4.3 for reference and troubleshooting.

The sign-in use case, outlined in Figure 4.3, follows a similar multi-actor workflow but emphasizes the secure retrieval and management of user credentials. Here, users initiate login via their chosen social provider, triggering the SDK to communicate with Auth0 for credential validation. Upon successful authentication, the SDK coordinates with Executors and the system backend to reconstruct the user’s private key using securely stored shares, ensuring that no single entity within the system holds the complete key at any time. This distributed key management strategy not only reduces the risk of key compromise but also supports features like account recovery and multi-factor security. Should any errors surface during authentication or key reconstruction, they are promptly detected and managed as detailed in Table 4.4, maintaining clear pathways for error reporting and user assistance. The entire authentication and key restoration sequence is meticulously tracked, with extensive logging and status indicators managed within the SDK to provide real-time feedback to both users and system administrators.

A distinct use case highlighted in Figure 4.4 enables users to view and interact with their private key and its associated shares. Access to this functionality is granted only after successful authentication, ensuring that only the legitimate account owner can retrieve sensitive cryptographic material. The system provides a secure interface through which the user, leveraging the SDK, can view, export, or manage their private key and the distributed shares, enabling secure external storage or backup outside the hosted platform. This guarantees user sovereignty over their cryptographic assets and supports various personal security policies, as detailed in the relevant documentation and referenced within the figures and tables. Logging, auditing, and user consent are integral to these processes to prevent unauthorized access or key exposure. Cross-references to Table 4.3 and Table 4.4 within the documentation establish a cohesive framework tying error codes and workflow statuses to specific stages in the authentication and key management flows, facilitating easier debugging, user support, and compliance verification. Overall, the design efficiently coordinates between user actions, SDK logic, system backend, Executors, and Auth0, offering a seamless, secure, and user-centric approach to both social login and private key management while retaining transparency through extensive documentation and figure/table references.
